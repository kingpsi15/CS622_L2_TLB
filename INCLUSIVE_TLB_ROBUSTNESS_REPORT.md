## 1. Bugs found in `tlb.cc.inclusive.sa`/`tlb.hh.inclusive.sa`, fixed, and proved

| # | Bug | Evidence | Root cause | Fix |
|---|---|---|---|---|
| 1 | `l2_remove(Addr va)` is not ASID/PCID-aware | `demapPage()` calls `l2_remove(va)` with no `asn`; `l2_remove` masks the low 12 bits of both sides before comparing — exactly the bits `concAddrPcid()` uses to carry the PCID. Code read confirms: `(entries[i].vaddr & ~0xFFF) == (va & ~0xFFF)` matches **any** process's L2 entry for that VPN, not just the caller's. | `demapPage`/`l2_remove` never had an address-space concept; only `l2_insert`/`l2_lookup` happened to compare the *full* concatenated key. | `tlb.cc.inc.fixed`: `l2_remove(Addr va, uint64_t asn)` builds the same `concAddrPcid(pageAligned, asn)` key `l2_insert`/`l2_lookup` use and does an exact match; `demapPage` now passes its `asn` through. |
| 2 | `serialize()`/`unserialize()` cover only L1 | Original: checkpoint `m5.cpt` after a 2048-page capacity run has `_size=64` (L1 full) and `Entry0..Entry63`, **zero** `l2Sets`/`L2Entry*` keys (`grep -c "l2Sets\|L2Entry" m5.cpt` → 0). Restoring that checkpoint under `TimingSimpleCPU` fires **20/20 `TLBCHK INCLUSION-VIOLATION … has NO L2 copy`** warnings at tick 89602500, immediately after `unserialize`. | The L2 state (`l2_sets`/`l2_sets[].entries[]`) was simply never added to `serialize`/`unserialize` when the L2 was added. | `tlb.cc.inc.fixed` serializes `l2Sets`/`l2Ways`/`l2_lruSeq`/`l2Count` plus each valid L2 entry's own section, and restores them, re-deriving each entry's set from its own `vaddr` (see finding below — no stored index). Geometry mismatch between checkpoint and running config is a `fatal()`, not a silent truncation. |
| 3 | (found while fixing #2) gem5's checkpoint format is **positional**, not purely key/value | Twice: `SERIALIZE_SCALAR(l2Sets)` placed *after* the `Entry%d` loop landed inside `[…Entry63]`, not `[…dtb]` (`Can't unserialize 'l2Sets'` on restore); then a `paramOut("l2Idx%d", …)` interleaved *between* sibling `L2Entry%d` sections landed inside the *previous* sibling (`Can't unserialize 'l2Idx0'`) even though a parent-scalar block preceded the whole loop. A scalar written after **any** child `serializeSection()` call is attributed to the most-recently-opened child, not the parent, for the rest of the function. | Not a bug in the shipped file — a bug we introduced while fixing #2, caught by re-testing before calling it done (see §6). | Final design writes every parent scalar (`l2Sets/l2Ways/l2_lruSeq/l2Count`) before *any* child section opens, and stores **no** per-entry index at all: `unserialize` recomputes each restored entry's set via `l2SetIndex(vaddr>>PageShift)` (same hash used at runtime) and drops it into the first free way of that set. Verified: `grep` shows `l2Sets=128` 3 lines after `[system.cpu.mmu.dtb]`, and `L2Entry0` appears as its own section with no `l2Idx` line anywhere. |
| 4 | No runtime-selectable architecture (static audit item) | `tlb.hh.inclusive.sa` hard-codes `L2_SETS=128`/`L2_WAYS=4`, XOR-7 hash, LRU; `tlb.cc.inclusive.sa` has no SimObject params for any of it. | Compile-time constants. | `tlb.cc.inc.fixed`/`tlb.hh.inc.fixed` read `TLB_L2_GEOM` (64x8\|128x4\|256x2\|fa), `TLB_L2_HASH` (mod\|xor7\|xorfold), `TLB_L2_REPL` (lru\|fifo\|random\|plru), `TLB_L1_SIZE` once at TLB construction (documented at the top of `tlb.cc.inc.fixed`); one binary covers every combination. Unknown values `fatal()` by name. |

All four are **fixed** in `gem5/src/arch/x86/tlb.cc.inc.fixed` + `tlb.hh.inc.fixed` (new files; originals untouched) and `robustness/patches/inc_fixed.diff` (against the `.inclusive.sa` snapshot).

**Audit items investigated and found NOT to be live bugs in SE mode:**
- *"`concAddrPcid` ORs PCID into low address bits, insert path excludes page-offset bits"* (audit §3.3): true for **FullSystem** (`trie.insert(vpn, MaxBits-logBytes, …)` drops the low 12 bits, which is exactly where the PCID lives, so FS-mode PCID tagging is a real residual limitation — documented, not fixed, since this lane's matrix and the user's stated priority are SE mode and fixing it needs an actual ASID field on `TlbEntry`, a shared x86 ISA struct touched by all five lanes). In **SE mode** the trie uses the full `MaxBits`, so the PCID *does* distinguish entries; this is why bug #1 shows up as a spurious cross-process **invalidation**, not a cross-process **data leak** — confirmed by 0/0 oracle mismatches across the entire SE matrix and all 31 passing SPEC benchmarks on both the original and fixed binaries.
- *No L2 serialization in checkpoints* — this **is** bug #2, confirmed live.
- *Back-invalidation under same-set storms* — reproduced on purpose by `tlbstress conflict` (built around the exact XOR-7 formula); `chkBackInvalidations` and `chkInclusionViolations=0` throughout confirm the back-invalidation path itself is correct (L2 eviction always finds and removes the L1 copy) — the only issue is hash quality, covered in §3.

## 3. Runtime-selectable architecture variants — battery and ranking

All variants are the **same fixed binary** (`gem5-inc-fixed/build/X86/gem5.opt`); only env vars differ. Battery: `tlbstress conflict 80 10` (built around the XOR-7 formula — adversarial for that specific hash) then `tlbstress capacity 2048 2` (general-purpose working-set sweep), 1 core, `AtomicSimpleCPU`. `chkInclusionViolations`/`chkOracleMismatch` are summed across both TLBs (dtb+itb); `L2hits`/`backinv` are `chkL2Hits`/`chkBackInvalidations`, i.e. correctness-relevant and effectiveness-relevant counters from the *same* checker that gates PASS/FAIL everywhere else in this report.

| variant | geom | hash | repl | L1 | L2 hits | back-inval | incl. viol. | oracle mismatch |
|---|---|---|---|---|---|---|---|---|
| default (= inclusive.sa shape) | 128×4 | xor7 | lru | 64 | 0 | 3130 | 0 | 0 |
| geometry: 64×8 | 64×8 | xor7 | lru | 64 | **1973** | **0** | 0 | 0 |
| geometry: 256×2 | 256×2 | xor7 | lru | 64 | 1925 | 20 | 0 | 0 |
| geometry: fully-assoc | fa (1×512) | xor7 | lru | 64 | **1973** | **0** | 0 | 0 |
| hash: mod | 128×4 | **mod** | lru | 64 | **1973** | **0** | 0 | 0 |
| hash: xor-fold | 128×4 | xorfold | lru | 64 | 0 | 3030 | 0 | 0 |
| replacement: FIFO | 128×4 | xor7 | fifo | 64 | 0 | 3130 | 0 | 0 |
| replacement: random | 128×4 | xor7 | random | 64 | 0 | 3151 | 0 | 0 |
| replacement: PLRU | 128×4 | xor7 | plru | 64 | 0 | 3130 | 0 | 0 |

| L1 size 128 | 128×4 | xor7 | lru | 128 | 0 | 3130 | 0 | 0 |

**Correctness across every variant: 0 inclusion violations, 0 oracle mismatches.** The fix does not trade correctness for any variant choice.

**Finding:** `tlbstress conflict` deliberately computes its colliding set with the *same* `((vpn>>7)&0x7f) ^ (vpn&0x7f)` formula the original code's `xor_7_hash` uses, to stress same-set eviction. Under the **default geometry+hash** (128×4, xor7), that adversarial set thrashes to 0 L2 hits / 3130 back-invalidations. Simply switching the hash to **mod** (same 128×4 geometry, same LRU) removes the pathology entirely (1973 hits, 0 back-invalidations) — as effective as *doubling associativity* (64×8) or going fully associative, **without** the extra tag-compare hardware those would cost. Replacement policy (FIFO/random/PLRU vs LRU) makes **no measurable difference** on this adversarial pattern: once 5+ distinct pages alias one 4-way set, any policy thrashes equally — this is a capacity/hash problem, not a replacement-policy problem. L1 size barely matters here because `conflict` is specifically an L2-indexing stress test (L1 32→128 only moved the needle from 0 to 19 hits in one configuration, consistent with noise from fewer evictions reaching L2 at all when L1 is larger).

**Best variant for this battery:** `TLB_L2_GEOM=128x4 TLB_L2_HASH=mod TLB_L2_REPL=lru` (unchanged geometry/associativity/replacement from the Mid-Review design — only the hash changes) — matches the effectiveness of doubling associativity at no extra hardware cost. **Caveat (not tested, time-boxed out):** `mod` is known in general to be weaker than XOR-style hashing against *strided* access patterns that are exact multiples of the set count (128); the adversarial test here specifically defeats XOR-7, so this ranking should not be read as "`mod` dominates `xor7` on all workloads" — only that it dominates on the one adversarial pattern this lane's test battery exercises, and that the project's own hash has an exploitable blind spot worth knowing about.

## 5. Checkpoint fix, proved dynamically

- **Before (original):** checkpoint of a populated TLB (`capacity 2048 2`, L1 full 64/64) → `m5.cpt` has **zero** `l2Sets`/`L2Entry*` keys. Restoring it under `TimingSimpleCPU` fires the checker's cap of **20/20** `TLBCHK INCLUSION-VIOLATION … has NO L2 copy` warnings at the first post-restore check, one per now-orphaned L1 entry.
- **After (fixed):** checkpoint of the same style of run (`capacity 128 2`) → `m5.cpt` has `l2Sets=128`/`l2Ways=4`/`l2_lruSeq`/`l2Count` correctly inside `[system.cpu.mmu.dtb]` (3 lines after the header) and a full set of `[system.cpu.mmu.dtb.L2Entry*]` sections with no stray `l2Idx` scalar anywhere — **static proof, confirmed by direct file inspection** (`/tmp/sahilag24/work/ckpt3/take/cpt.*/m5.cpt`). This is a structural, offline check of exactly what the fixed binary wrote to disk — not a timing-dependent claim.
- **Dynamic confirmation: the restore step itself completed cleanly; full-workload-to-stats-dump did not finish in time.** Three attempts (300 s, 1800 s, 3600 s timeouts) under `TimingSimpleCPU --caches --l2cache`. The third (1-hour) attempt's `simout.txt` shows `Switched CPUS @ tick 89612500 / switching cpus / **** REAL SIMULATION ****` — i.e. gem5 completed the atomic-warmup-to-Timing CPU switch, which is exactly where `unserialize()` and the checker's post-restore `chkInclusion()` call run. **Zero** `TLBCHK` lines appear in `simerr.txt` and no `fatal()`/`panic()` occurred — for comparison, the original (buggy) binary's equivalent run printed its first of 20 `TLBCHK INCLUSION-VIOLATION` lines *immediately* upon reaching this same point, not minutes later. So the one check that directly exercises the fix (restore, then the inclusion check that follows it) ran and passed; what didn't finish was the *rest* of the `capacity 128 2` workload executing far enough under `TimingSimpleCPU` to reach gem5's end-of-run stats dump (`stats.txt` stayed at 0 bytes when the 3600 s `timeout` killed the process — `timeout` sends `SIGTERM`, which gem5 does not appear to catch to flush a final stats dump, so this is consistent with "still simulating" rather than "crashed"). The **original** binary's own restore-and-run (bigger workload, `capacity 2048 2`) *did* reach the stats dump, in ~27 minutes — so either checkpoint-restore under this CPU/cache combination has an inherent large fixed cost that this smaller workload's *remaining* instruction count didn't offset, or something after the restore point runs slower on the fixed binary specifically; this session did not have time to isolate which. Every other signal in this report (static file structure, 54-job SE matrix, 31-benchmark SPEC run, 11-variant sweep — all exercising the same L2 code paths, just not through checkpoint/restore) shows the fix behaving identically to a correct TLB, and the one checkpoint-specific check that *did* execute (the restore + immediate post-restore inclusion check) passed. **Recommended follow-up:** retake the checkpoint under `AtomicSimpleCPU` for the restore step too (removing `TimingSimpleCPU`/`--caches --l2cache` as a variable) to isolate whether the remaining slowness is restore-specific or an artifact of the Timing+cache combination seen elsewhere in this report, and/or just let a longer run finish to get the final `chkInclusionViolations`/`chkOracleMismatch` numbers.
- Both take→restore pairs (`capacity 2048 2` on the original, `capacity 128 2` on the fixed) ran under `TimingSimpleCPU --caches --l2cache`; the *original's* run completing in ~27 minutes while stock gem5 limitations elsewhere in this report (§4) show no such pattern suggests checkpoint-restore itself carries a large fixed wall-clock cost in this build, independent of workload size — plausible but not confirmed, since the fixed binary's equivalent run is the one data point that would confirm it and it did not finish.
